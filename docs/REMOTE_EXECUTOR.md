# Delegated executor

| Identity | Entry point | Scope |
| --- | --- | --- |
| edge | Existing read connector or dedicated edge bearer on loopback | Reads on projects granted to edge |
| executor:default | Loopback MCP with the distinct executor bearer | Project and recipe from an active owner-issued task grant |
| local | Local CLI and owner bearer | Owner administration and approval |

Prepare the isolated service with the `canary` or `synthetic` environment flag. Register one approved fixture root and create a short-lived grant for `executor:default`. Keep the credential files in the broker state directory. Load the executor bearer into the client in memory through the client's secret mechanism. Keep the owner credential with the controller.

## Grant profiles

`edge-bridge --state-dir <state> grant-create <project_id>` accepts `--requester <principal>` (default `executor:default`), `--ttl-minutes <1..=1440>` (default `60`), and either `--profile` or manual `--writable-path` / `--recipe` flags (`--profile` conflicts with `--writable-path` and `--recipe`). Under any grant, old or new, a delegated principal can never create or patch files under `_pro/inbox/`.

| Command | Categories | Writable paths | Allowed recipes | Notes |
| --- | --- | --- | --- | --- |
| `edge-bridge --state-dir <state> grant-create <project_id> --profile pro-review` | `read`, `git_read`, `write`, `execute_recipe` | `_pro/**` (create-only; `_pro/inbox/**` denied) | `python_tests`, `powershell_script` | None of the `work_*` tools is available. Create new files under `_pro/outbox/` and `_pro/reports/`. |
| `edge-bridge --state-dir <state> grant-create <project_id> --profile pro-agent` | `read`, `git_read`, `write`, `patch`, `work_area`, `execute_recipe` | `_pro/**` (create-only outside `_pro/work/<workspace>/**`; mutable inside exact-case `_pro/work/<workspace>/**`; `_pro/inbox/**` denied) | `python_tests`, `powershell_script`, `python_tests_work` | Enables `work_copy`, `work_edit`, `work_move`, `work_delete`, `work_diff`, `work_export_diff`, and hash-checked overwrites inside `_pro/work/<workspace>/**`. Live project files stay read-only. |
| Bare `edge-bridge --state-dir <state> grant-create <project_id>` (no `--profile` or `--writable-path`) | `read`, `git_read`, `execute_recipe` | `[]` | Requested `--recipe` values (default `python_tests`) | Passing explicit `--writable-path` patterns adds `write`, `patch`, and `checkpoint`; a writing grant can queue runs only when its single writable path is `_pro/**`. |

`powershell_script_work` is refused everywhere (`grant-create`, `task_submit`, and `worker`) with `POWERSHELL_SCRIPT_WORK_UNSUPPORTED`.

## Delegated MCP tools (46 total)

The MCP catalog exposes **46 tools** (33 legacy, 6 v0.4.0, 7 v0.5.0). `edge` stays strictly read-only: it cannot call `job_wait` or any `work_*` tool, cannot use the new line-range or search options, and keeps `file_list` capped at 100 entries.

- **Grant inspection:** Call `policy_view` with `project_id` and optional `grant_id` to inspect `grant` (`grant_id`, `permitted_categories`, `writable_paths`, `denied_paths`, `allowed_recipes`, `export_scope`, `limits`, `expires_at`) and, when `work_area` is granted, `work_area` (`root: "_pro/work/"` and existing `workspaces`, up to 16). When a delegated call omits `grant_id`, the bridge selects the newest non-revoked, non-expired grant valid for that principal, project, host, and current policy revision; with an explicit `grant_id`, that specific grant is checked or refused.
- **Read options (non-`edge`):** `file_read`, `file_view`, and `file_read_batch` (up to 32 items) accept optional 1-based `start_line`/`end_line` (up to 2,000 lines, mutually exclusive with `offset > 0`; still capped at 32 MiB file and 65,536 characters per page). `file_search` accepts `context_lines` (`0..=5`), `file_glob` (1–64 ASCII chars, no `/`, `\`, or `..`), and linear-time `regex` (256 KiB compile/DFA limit; skips files over 2 MiB; up to 100 hits). `file_list` accepts `limit` up to 500 (default 50) and returns `{path, kind, size}`. `file_patch` rejects 0 or >64 edits before authorization.
- **Background runs and `job_wait`:** `task_submit` (`project_id`, `task_id`, `operation_id`, optional `grant_id`, `recipe`, `args`) persists a `queued` run (`execution_mode: "queue_only"`) and returns `run_id` immediately so the model can keep reading or editing. A grant may have at most **8** active or queued runs at once (`RESOURCE_BUDGET_EXCEEDED`); reusing the same `operation_id` and payload on a retry returns the existing run even at the cap. Collect results with `job_wait` (`job_ids`: 1–16 unique `run_id`s; `timeout_seconds`: `0..=20`, default `15`, `0` for an immediate batch check; `wait_for`: `"any"` or `"all"`; `include_output`: default `true`; `output_limit_bytes`: `1..=32,768`, default `16,384` per terminal run; max 2 concurrent waits per caller, `RESOURCE_BUSY` with `retry_after_ms: 500`). Use `job_output` with `next_seq` when more output is needed. `task_get` returns up to 50 runs for one `task_id` with `workload_report` on delegated runs. `job_cancel` cancels a run under the same grant, re-authorizing against the stored recipe. `artifact_list` lists sealed manifests for the caller and grant (`execution_outcome`, `agent_outcome`, `verification_outcome`, `verdict`); pass `manifest_id` to `artifact_read` as `artifact_id`.
- **Work-area tools (`pro-agent` / `work_area` only):** Workspaces live at exact-case `_pro/work/<workspace>/` (`^[a-z0-9][a-z0-9_-]{0,39}$`, max 16 workspaces per project, sharing the `_pro/` quota of 2,000 files, 256 MiB, and 8,192 walk entries). Baseline hashes are stored outside `_pro/work/` in `<state>/work-manifests/<project_id>/<workspace>.json`.
  - `work_copy`: Copy 1–64 project files or subtrees (`exclude_generated` default `true`, `overwrite_existing` default `false`; up to 500 files, 4 MiB/file, 32 MiB/call, 20,000 walked entries; silently skips hidden/secret files, `_pro/`, links, and hardlinked files), or copy 1 file within the same workspace (`within_workspace: true`, `from`, `to`).
  - `work_edit`: Atomic multi-file search-and-replace inside `_pro/work/<workspace>/`: 1–32 files, 1–64 total replacement hunks, max 1 MiB/file, max 4 MiB/call, optional `expected_hash`, `replace_all` (default `false` requires a single match). All edits succeed or nothing changes. (`file_write` and `file_patch` also permit hash-checked overwrites strictly inside `_pro/work/<workspace>/**` under `work_area`.)
  - `work_move`: Rename or move 1 regular file strictly inside `_pro/work/<workspace>/` (`from`, `to`, optional `expected_from_hash`, `overwrite`, `expected_to_hash`), updating the bridge manifest.
  - `work_delete`: Delete 1–64 files strictly inside `_pro/work/<workspace>/` (optional `expected_hashes`), or set `delete_workspace: true` to remove the whole workspace and its manifest (walk cap 8,192 entries; refuses links) to free `_pro/` quota.
  - `work_diff`: Read-only unified diff (max 4 MiB) and per-file stats comparing `_pro/work/<workspace>/` against live project files using the bridge manifest. Accepts optional `paths` (1–64), `summary_only`, `expected_diff_sha256`, and character `offset`/`limit` (default 32,768, max 65,536). Flags baseline drift (`drifted_files`) and live-project collisions (`conflict_files`), and omits bodies for binary or >1 MiB files.
  - `work_export_diff`: Create one new `git apply`-compatible `.diff` file directly under exact-case `_pro/outbox/` (`_pro/outbox/[a-zA-Z0-9][a-zA-Z0-9._-]{0,120}.diff`, create-only, max 1 MiB). Refuses empty diffs, drifted baselines unless `allow_drifted: true`, and binary or >1 MiB changes (use `edge-bridge work-apply` for those).

## Applying workspace changes locally (`work-apply`)

`edge-bridge work-apply` is an owner-only CLI command and is never exposed as an MCP tool. It reads baseline hashes from `<state>/work-manifests/<project_id>/<workspace>.json` and refuses with `VERSION_CONFLICT` if any modified or deleted project file changed after `work_copy`, or if an added file already exists in the project.

```powershell
# 1. Dry run (default): prints planned changes, drift check, and unified diff without touching disk
edge-bridge --state-dir <state> work-apply <project_id> <workspace>

# 2. Apply atomically (all files or none) and record a patch journal
edge-bridge --state-dir <state> work-apply <project_id> <workspace> --confirm

# 3. Roll back using the journal_id printed by work-apply --confirm (refuses to overwrite later edits)
edge-bridge --state-dir <state> rollback-patch --project-root <project> --journal-id <journal_id>
```

## Owner queue worker

`execution_mode: queue_only` confirms durable admission. The local owner starts `edge-bridge --state-dir <state> worker --runtime-root <trusted-checkout>` from the interactive Windows desktop. The runtime checkout needs the Bridge Python package and its existing `.venv`. The runtime and state directories must be outside the project. Add `--once` to drain the queue and exit when it is empty. The worker fails a delegated run with `PERSISTENT_ENVIRONMENT_HOLDS_CREDENTIALS` while the persistent user or machine environment holds an entry that looks like a credential, because a run can read it; `edge-bridge environment-check` lists the names, and `--allow-environment-credentials` runs standard recipes anyway (it never applies to `python_tests_work`).

To allow `python_tests_work`, the owner must explicitly pass `--allow-work-exec` to `worker`. Without `--allow-work-exec`, the worker refuses `python_tests_work` immediately with `WORK_EXEC_NOT_ENABLED` without preparing a snapshot. **Recommendation: leave `--allow-work-exec` off unless you accept the sandbox registry risk.** Measured on one PC with `scripts/probe_work_sandbox.ps1`, sandboxed code has no network and no folder access outside its snapshot, but Windows user name and profile paths reach the code and it can list `HKCU\Software`, `HKLM\Software`, and `HKCU\Environment`; code written by the remote model can read registry data of installed programs and return it in captured output, while the persistent-environment check covers only the two environment keys by name and pattern. Without `--allow-work-exec`, a `pro-agent` model can still copy, edit, diff, and export patches in `_pro/work/` and run the project's own `python_tests`, but cannot test its own workspace edits. See `docs/KNOWN_LIMITATIONS.md`.

One worker per state directory claims delegated submissions for the local host. The owner can still approve a local-only Python submission with `run-queued-python-tests`.

| Recipe | Request | Snapshot scope |
| --- | --- | --- |
| `python_tests` | Empty `args` | Runs project files only (never `_pro/` or any grant-writable folder) with standard-library `unittest` (`python -I -S -B`, no third-party packages). Discovers eligible `.py` and `.json` files up to 6 levels down in 1,000 visible entries. Credential-style files and folders hidden from remote principals (`is_hidden_from_remote`) are skipped without copying, counting, hashing, or naming them. Needs at least one top-level `tests/test_*.py` (`tests/__init__.py` is optional: when present, runs `discover -s tests -t .`; when absent, puts the snapshot root on `sys.path` and runs `discover -s tests` without creating files). Shares snapshot limits with `python_tests_work`: max 128 snapshot files, 256 KiB per file, 4 MiB total, 128 KiB request frame. Limit refusals report which limit was exceeded and the measured value. |
| `python_tests_work` | `args`: `[workspace]` or `[workspace, test_selector]` (`tests/test_<name>.py` or `tests.test_<name>[.<Class>[.<method>]]`) | Requires `--profile pro-agent` grant (`work_area` + `python_tests_work`), worker `--allow-work-exec`, a clean persistent-environment check (mandatory; `--allow-environment-credentials` does not apply), and a bridge-side workspace manifest. Runs standard-library `unittest` only (`python -I -S -B`, no third-party packages) on a snapshot of `_pro/work/<workspace>/`: up to 128 `.py`/`.json` files, 256 KiB per file, 4 MiB total, 1,000 visible entries, depth 6; links, hardlinked files (`n_links != 1`), and hidden files are refused or omitted. Works with or without `tests/__init__.py` (single-test selectors work in both layouts without creating files). Enforces a Win32 Job Object CPU hard cap of `min(50%, grant.limits.max_cpu_percent)`. Manifest uses `executor_identity: "local-owner-mxc-work-copy-worker"` and `verification_outcome: NOT_TESTED` (never reports live project files as tested). |
| `powershell_script` | `args` contains one canonical project-relative `.ps1` path | Runs a project script outside grant-writable folders (`SCRIPT_INSIDE_REQUESTER_WRITABLE_PATH` refuses `_pro/**`). Snapshots the one script (<= 64 KiB) and invokes pinned PowerShell 7.6.10 with `-NoProfile -NonInteractive -File`. Extra script arguments are refused. |
| `powershell_script_work` | Refused everywhere | Not supported (`POWERSHELL_SCRIPT_WORK_UNSUPPORTED`). |

The durable run stays `admitted` while the supervisor stages the snapshot and runs its containment preflight. Rust uses the broker's protected filename policy in `crates/bridge-core/src/files.rs` to select the permitted source paths. The Python supervisor checks the exact allowlist before reading any staged source. Immediately before creating the workload process, the supervisor waits for a one-use launch reply. The transaction that authorizes launch and marks the run `running` checks the original grant, its expiry, project revision and cancellation together. Every retry repeats that check against the current state. A denied launch or failed containment canary ends preparation without creating the workload process. A cancellation committed after that transaction follows the running cancellation path. The supervisor locks and hashes the pinned Codex image for each preflight and workload launch. It keeps the image and its resolved directory path locked through process creation. For PowerShell it holds the same locks until the job tree exits because Codex starts that child asynchronously.

`job_output` pages the bounded, redacted capture by `next_seq`. The Python runner captures stdout and stderr in one stream of at most 256 KiB, or less when the grant sets a lower `max_output_bytes`, exposed as `combined` in chunks of at most 4 KiB. Request denial and supervisor failure codes use `stderr`. The worker stores the run output chunks in one transaction. The owner can inspect a signed manifest for captured output and containment provenance after the supervisor confirms workload startup and the process tree exits. The manifest and `job_get.workload_report` label the exit code and parsed counts as reported by the workload. The workload controls its output. The independent verification field reads `NOT_TESTED` for workload-reported results, including previously stored delegated runs with sealed capture. PowerShell has no test-count parser. The worker rejects non-exportable request metadata before starting the supervisor. An evidence rejection or early supervisor exit with confirmed process-tree cleanup fails the affected run and the worker continues draining the queue. Worker store operations retry temporary SQLite contention with a finite budget. If evidence finalization fails in the store, the worker stops and the run becomes `unknown` immediately or at the next startup if the store is still unavailable. The worker resolves completion and cancellation in one transaction that commits the terminal state and its matching signed manifest together, then publishes any local evidence files. Cancellation committed before that decision wins, and cancellation requests after commit return the recorded state.

A queued cancellation prevents admission. A running cancellation asks the supervisor to terminate its Job Object. The worker confirms the outer process tree has exited before recording `cancelled`. If the supervisor hangs, the worker terminates the outer Job Object and confirms its exit. Cancellation before launch and forced cleanup without a receipt produce no workload manifest. The worker removes the workspace and raw supervisor state after confirmed exit. On restart, the worker holds the exclusive lease while sweeping leftovers from dead workers. Windows terminates their process trees when their Job Object handles close. A cleanup failure is reported in the signed manifest and the affected file is left for the next sweep. An unfinished delegated run becomes `unknown` and is never replayed automatically.

| Resource | Current behavior |
| --- | --- |
| Concurrency and wall time | One delegated workload per worker, a supervisor deadline of `min(60 s, grant.limits.max_duration_seconds)`, and an outer deadline (`+15 s`) for a stalled supervisor. A grant value of `0` is refused with `INVALID_GRANT_LIMITS`. |
| Containment | Per-job MXC preflight, no network, `min(8, grant.limits.max_processes)` processes, and `min(768 MiB, grant.limits.max_memory_mb)` of memory in the recipe job. A grant value of `0` (or one Windows rejects) is refused with `INVALID_GRANT_LIMITS`. |
| Snapshot and workspace | The snapshot input limits above apply (`python_tests` and `python_tests_work`: 128 files / 256 KiB per file / 4 MiB total / 1,000 entries; `powershell_script`: 1 script <= 64 KiB). Refusals report which snapshot limit was exceeded and the measured value. The supervisor polls logical workspace file sizes (every 50 ms for standard runs, 25 ms for work-copy runs) and fails the run at more than `min(256 MiB, grant.limits.max_storage_bytes)` (32 MiB under default grant limits), more than 16,384 entries, or an observed reparse point. The scanner samples logical file sizes; there is no enforced byte bound on overshoot, and alternate data streams and filesystem metadata fall outside the sample. |
| Output | Capture is limited to `min(256 KiB, grant.limits.max_output_bytes)` per run and chunked as described above. Stored `run_output_chunks` are pruned to the most recent 200 terminal runs while keeping `durable_runs` and `evidence_manifests` rows. |
| Queue and CPU | A grant may hold at most 8 active or queued runs (`RESOURCE_BUDGET_EXCEEDED`; idempotent replay of an existing `operation_id` still succeeds). For `python_tests_work`, the worker and supervisor enforce a Win32 Job Object CPU hard cap of `min(50%, grant.limits.max_cpu_percent)` and refuse the run with `INVALID_GRANT_LIMITS` if the cap cannot be set. For standard recipes (`python_tests`, `powershell_script`), `grant.limits.max_cpu_percent` is checked for `!= 0` but not applied as a CPU cap. |

A full state volume stops the worker when it cannot write controller state or finalize a run. Put the state directory on a volume with a quota that leaves room for controller writes, or reserve enough free-space margin for the workload and its controller records.

For the current stdio read connector, leave its server-side identity set to `edge`. HTTP activation needs a separate private connector configuration to the loopback MCP URL. The tunnel client's extra-header setting can read the executor secret from an external file reference. Verify the exact connector profile, destination and allowed client identity at setup. Keep raw profiles and credential references entirely within the runtime.
